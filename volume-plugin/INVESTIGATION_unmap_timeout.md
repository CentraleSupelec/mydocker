# Volume Plugin `Create` Timeout — Investigation Report

**Date:** 2026-05-11
**Host:** `tf-preprod-manager`
**Plugin:** `centralesupelec/mydockervolume:latest` (image `jq422pa7.gra7.container-registry.ovh.net/mydocker-public/mydockervolume:latest`)
**Mode:** `DRIVER_MODE=RBD`, pool `mydocker-preprod`
**Affected operation:** `docker volume create --driver centralesupelec/mydockervolume`

---

## 1. Symptom

```
$ docker volume create \
    --driver centralesupelec/mydockervolume \
    --opt size=5120 test-volume-timing4
Error response from daemon: create test-volume-timing4:
  Post "http://plugin.moby.localhost/VolumeDriver.Create":
  context deadline exceeded
```

Volume is actually created in Ceph (rbd image present, mkfs done), but the CLI sees a timeout. Same outcome regardless of requested size (1 GiB, 5 TiB, etc.).

---

## 2. Root Cause — Full Chain

The error is the Docker daemon abandoning the HTTP call to the plugin. Three layers stack up and the bottom one is the real bug.

### 2.1 Docker daemon side — 2-minute deadline

[`moby/daemon/volume/drivers/proxy.go`](https://github.com/moby/moby/blob/master/daemon/volume/drivers/proxy.go) (generated by `pluginrpc-gen`):

```go
const (
    longTimeout  = 2 * time.Minute
    shortTimeout = 1 * time.Minute
)

...

pp.CallWithOptions("VolumeDriver.Create", req, &ret,
    plugins.WithRequestTimeout(longTimeout))
```

[`moby/pkg/plugins/client.go`](https://github.com/moby/moby/blob/master/pkg/plugins/client.go) applies the timeout to the request context:

```go
if opts.Timeout > 0 {
    ctx, cancelRequest = context.WithTimeout(req.Context(), opts.Timeout)
    req = req.WithContext(ctx)
}
```

(Note: the often-quoted `defaultTimeOut = 30 * time.Second` in `client.go` is **only** the cap of the retry backoff — it is **not** the request deadline. The actual request deadline is the 2 min above.)

So if the plugin doesn’t return a body within 120 s, dockerd cancels the HTTP request and returns `context deadline exceeded` to the CLI — even though the plugin continues running and eventually finishes.

### 2.2 Plugin driver side — also 2-minute shell timeout

`pdesgarets/docker-volume-rbd` (`go.mod` replace of `wetopi/docker-volume-rbd`):

`lib/sh.go`:
```go
var defaultShellTimeout = 2 * 60 * time.Second   // 2 minutes
```

`lib/rbd-driver-private.go::unmapImage` calls `rbdsh("unmap", ...)` → `shWithDefaultTimeout("rbd", ...)`. So the `rbd unmap` CLI invocation itself is capped at 2 min on the Go side.

Note: `shWithTimeout` does **not** kill the child process when the timer fires; it just returns `"timeout reached"` and lets the child leak. Each timed-out call leaks one `rbd unmap` zombie.

### 2.3 The actual stuck operation — `rbd unmap` waiting on udev

Captured kernel stack of a live, stuck `rbd unmap` child (PID 1912921 in our run):

```
[<0>] do_poll.constprop.0+0x22a/0x390
[<0>] do_sys_poll+0x1c8/0x250
[<0>] __x64_sys_poll+0x3d/0x140
[<0>] x64_sys_call+0x3f3/0x1fa0
[<0>] do_syscall_64+0x56/0xb0
```

Open file descriptors:
```
3 -> socket:[292856928]                                  ← netlink (libudev monitor)
6 -> /sys/bus/rbd/remove_single_major                    ← sysfs trigger (already written)
```

What `rbd unmap` does:
1. Writes the device-id to `/sys/bus/rbd/remove_single_major` — kernel actually removes the rbd device synchronously.
2. Calls `libudev` to wait for the udev `remove` event confirming the disappearance.
3. Loop times out after ~120 s if the event never arrives.

Inside the plugin’s mount namespace `/run/udev/` was missing entirely:
```
$ nsenter -t <plugin-pid> -m -- ls /run/udev/control
ls: cannot access '/run/udev/control': No such file or directory
```

`config.json` for the plugin only binds `/lib/modules`, `/dev`, `/etc/ceph`, `/sys`, `/mnt/mydocker-fs` — no `/run/udev`. So libudev’s monitor never sees the event, regardless of host udev daemon state.

Net effect: every Create burns ~120 s on the unmap step alone, exactly at the dockerd timeout boundary.

### 2.4 Sequence per Create call

From the plugin debug log (compressed):

| Time   | Step                                   | Duration   |
|--------|----------------------------------------|------------|
| t+0s   | `volume-rbd Request=Create`            | —          |
| t+0s   | `connect to ceph`                      | <0.1 s     |
| t+0s   | `checking if exists`                   | <0.1 s     |
| t+0s   | `rbd.Create` (RADOS metadata)          | <0.1 s     |
| t+0s   | `rbd map`                              | <1 s       |
| t+0s   | `mkfs.ext4 -O mmp` (1 GiB image)       | <1 s       |
| t+0s   | `rbd unmap` start                      |            |
| **t+120s** | `rbd unmap: timeout reached` (Go shell timer fires) | **120 s** |
| t+120s | `connection shutdown from ceph`        | —          |
| t+120s | return `200 {}` to dockerd             | — (often after dockerd already gave up) |

mkfs/map/create are all fast even at 5 TiB. The entire 2-min cost is in waiting for a udev event that cannot arrive.

## 3. What was tried

### 3.1 Bind-mount `/run/udev` into the plugin — **did not fix**

Edited `/var/lib/docker/plugins/<id>/config.json` of a local plugin, added:

```json
{
  "name": "udev",
  "source": "/run/udev",
  "destination": "/run/udev",
  "type": "bind",
  "options": ["rbind"]
}
```

Verified inside plugin ns: `/run/udev/control` visible. Host `systemd-udevd` active. **Unmap still hung 120 s.**

Reason: even with `/run/udev` bound, `libudev`’s netlink-based monitor inside the plugin namespace does not receive the kernel uevent for the device removal. Possibly requires PID-host or different namespace handling; investigating further was deprioritized in favor of a working workaround.

### 3.2 `--options noudev` flag on `rbd unmap` — **not supported**

`rbd unmap`’s only recognized `--options` value in the in-container Ceph CLI is `force`. `noudev` is valid for `rbd map` only. Passing it to `unmap` is silently ignored.

### 3.3 Shim `/usr/bin/rbd` to fire-and-forget on `unmap` — **WORKS**

Replaced `/usr/bin/rbd` in the plugin rootfs with a shell wrapper that, when invoked with the `unmap` subcommand, launches the real binary in the background and immediately exits 0. The kernel still removes the device asynchronously; the plugin returns to dockerd in milliseconds.

```sh
#!/bin/sh
# /usr/bin/rbd  — shim
for a in "$@"; do
  if [ "$a" = "unmap" ]; then
    /usr/bin/rbd.real "$@" >/tmp/rbd-unmap.log 2>&1 &
    exit 0
  fi
done
exec /usr/bin/rbd.real "$@"
```

## 5. Reparation plan

The shim is a confirmed workaround. Long-term fix should live in the driver code and ship in the plugin image. Three coordinated changes recommended.

### 5.0 Correctness constraint (NON-NEGOTIABLE)

The MyDocker pipeline relies on synchronous unmap semantics. The build flow is:

1. Backend builder maps a rbd volume.
2. Writes student data into the mounted filesystem.
3. **Unmaps it** to release watchers/locks on the image.
4. Hands the volume to a Swarm worker.
5. Student container starts and calls `Mount` on the freshly-unmapped image.

If step 3 returns before the kernel has finished releasing the device, step 5's `rbd map` races against an in-flight removal — watcher locks linger, fs may be in inconsistent state, the student-container start can fail or (worse) silently succeed on stale state. Builder reports green, customer-side failure surfaces downstream.

**Any fix must preserve**: `unmapImage` blocks until the kernel has fully released the device. What it must NOT do is block on libudev (the broken path).

Earlier drafts of this document recommended a fire-and-forget goroutine wrapping `unmapImage` and a `/usr/bin/rbd` shim that backgrounds the call. Both **violate the constraint above** and are retracted as primary fixes. They remain useful only as throwaway diagnostic tools (the shim plugin lets us snapshot the bug without losing the host for 2 minutes per probe).

### 5.1 Driver: poll sysfs for kernel-side release (PRIMARY FIX, correctness-preserving)

**File:** `lib/rbd-driver-private.go` in the `pdesgarets/docker-volume-rbd` fork (already a `replace` target in `go.mod`).

**Idea:** the kernel sysfs entry `/sys/bus/rbd/devices/<id>` disappears the moment `rbd_dev_image_release` finishes. That's the same signal `rbd unmap` waits for via libudev. We can wait on it directly without involving libudev at all.

Sketch (rough; tighten before merging):

```go
func (d *rbdDriver) unmapImage(imageName string) error {
    logrus.Debugf("volume-rbd Name=%s Message=rbd unmap (sysfs-wait)", imageName)

    target := filepath.Join(d.conf["pool"], d.conf["namespace"], imageName)

    // Resolve the rbd device id from the alias path before we trigger unmap.
    // d.getTheDevice(imageName) returns e.g. /dev/rbd/<pool>/<image>
    // We need the numeric id (the "N" in /dev/rbdN / /sys/bus/rbd/devices/N).
    id, err := resolveRbdDeviceID(d, imageName)
    if err != nil {
        // Already unmapped or never mapped — nothing to do.
        return nil
    }

    sysfsDir := fmt.Sprintf("/sys/bus/rbd/devices/%d", id)

    // Trigger the unmap via the existing CLI. shWithTimeout still applies,
    // but we *expect* it to time out on the libudev wait — that's fine,
    // because the kernel has already started teardown and we'll wait for
    // sysfs to drop the entry below.
    go func() {
        _, _ = d.rbdsh("unmap", target)
    }()

    // Poll the sysfs entry until it disappears, with a real upper bound
    // larger than the dockerd 2 min cap so we never claim done prematurely.
    deadline := time.Now().Add(5 * time.Minute)
    for {
        if _, err := os.Stat(sysfsDir); os.IsNotExist(err) {
            return nil
        }
        if time.Now().After(deadline) {
            return fmt.Errorf("unmap %s: sysfs entry %s did not disappear within deadline",
                imageName, sysfsDir)
        }
        time.Sleep(50 * time.Millisecond)
    }
}
```

Notes:

- `resolveRbdDeviceID` reads `/sys/bus/rbd/devices/*/name` (and matches pool+image) before triggering unmap. The existing driver already has `getTheDevice` returning the alias path; we can either parse it or do a fresh enumeration.
- The 5-minute deadline is generous and only meaningful as a guardrail. Kernel-side teardown on a properly mapped rbd device completes in milliseconds even on busy clusters in our environment.
- We *do* still call `rbd unmap` to trigger the teardown. Its 120 s libudev hang is now harmless because we ignore its exit and read the kernel state directly.
- Same logic must cover the `Unmount`/`Remove` paths (`FreeUpRbdImage` → `unmapImage`). Both end up calling `unmapImage`; fixing it once is sufficient.
- Race with subsequent `Mount`/`map`: by construction, this function returns only when sysfs says the device is gone. Whoever maps next sees a clean slate. Preserves the MyDocker builder→swarm hand-off semantics.

Open questions before merging:

- Does the spawned `rbd unmap` goroutine leak? Yes, it will sit in libudev poll for 120 s before its internal shell timeout kills the bookkeeping. Need to either (a) accept the temporary leak, (b) `cmd.Process.Kill()` after sysfs says we're done, or (c) drop the CLI invocation entirely and write to `/sys/bus/rbd/remove_single_major` ourselves. Option (c) is cleanest but skips the cluster-side cleanup that `rbd unmap` does via librbd (image header watcher release). Verify which librbd-side work is mandatory vs done by the cluster on its own after device gone.

This fix is conservative, correctness-preserving, and decouples us from the host's libudev/systemd state. It also doesn't require us to close the root-cause investigation on the systemd side — the bug becomes irrelevant to the fast path even if a future host regresses.

## 6.5 Why now? Regression timeline

The plugin code path that defers `rbd unmap` after Create has existed unchanged for years. The bug surfaces today because the **Ceph CLI bundled in the plugin image** was upgraded.

`git log -p -- Dockerfile`:

| Date       | Commit    | Change                                                                                    |
|------------|-----------|-------------------------------------------------------------------------------------------|
| 2022-05-25 | `159bf75` | initial Ceph driver — `pacific` (16.x)                                                    |
| 2023-02-16 | `c69ad22` | bookworm + `pacific → quincy` (17.x)                                                      |
| 2024-05-22 | `a37705f` | **`quincy → reef` (18.x)**, bookworm builder + golang 1.22 (← regression introduced here) |

Current `Dockerfile` pins `ENV CEPH_VERSION=reef` in both the builder and runtime stages.

### What is NOT the cause (verified)

Initially suspected: a `rbd unmap` behavior change between Ceph releases. Checked against source:

```sh
diff <(awk '/static const char \*get_event_source/,/^}/' pacific/krbd.cc) \
     <(awk '/static const char \*get_event_source/,/^}/' quincy/krbd.cc)
# (empty)
diff <(awk '/static const char \*get_event_source/,/^}/' quincy/krbd.cc) \
     <(awk '/static const char \*get_event_source/,/^}/' reef/krbd.cc)
# (empty)

diff -u pacific/krbd.cc quincy/krbd.cc      # 28 lines changed, ALL cout→std::cout style
diff -u quincy/krbd.cc reef/krbd.cc          # 0 lines changed (files byte-identical)
```

`src/krbd.cc` udev-wait path is identical across pacific / quincy / reef. **Ceph CLI is not the regression.** (Earlier draft of this doc claimed Reef tightened udev waiting — that was wrong; the code has been the same since pacific.)

### What `a37705f` actually touched beyond Ceph

```diff
-FROM golang:1.16 as builder        +FROM golang:1.22 as builder
-FROM debian:bullseye ... pacific   +FROM debian:bookworm ... reef
-FROM debian:bullseye ... quincy    +FROM debian:bookworm ... reef
```

Two other delta sources in the same commit:

- **debian:bullseye → debian:bookworm.** Bookworm ships systemd 252 (vs bullseye’s 247), newer libudev, newer glibc, newer util-linux. Any of these could be the actual regression carrier — libudev’s netlink filter implementation and `udev_monitor_receive_device` SCM_CREDENTIALS handling have seen changes across that range.
- **Possibly different `ceph-common` udev rules** packaged for bookworm; the rules in `/lib/udev/rules.d/*rbd*` decide whether events get re-broadcast on the `"udev"` channel that libudev listens to (`get_event_source` returns `"udev"` when `KRBD_CTX_F_NOUDEV` is not set, with the comment "udev uevents don't cross network namespace boundaries and are therefore confined to the initial network namespace").

### Why the bug only manifested now

PID 1017 (the stuck plugin) started `Jan28`. That is when the host last pulled or restarted the reef-bearing image. Before that the host was running a previously-cached image (likely the quincy/bullseye one). The combined upgrade in `a37705f` first became active on the host at that moment.

Not yet proven by hard evidence which of the deltas (base image vs udev rules vs kernel) is the actual carrier. Possible the bug already existed in earlier configurations but was hidden because:

- small volumes finished mkfs in a fraction of the 120 s window and the unmap timeout was reached *after* dockerd already had the Create response in flight (race won by the plugin most times),
- earlier libudev/host config happened to deliver the event correctly inside the plugin ns,
- or nobody filed it because volumes did get created and the CLI error was tolerated.

### Confirmation commands to run on host


### Action item

The fix is the same regardless of which sub-component flipped: the driver should not synchronously block on `rbd unmap` (kernel already does the removal when sysfs write returns). Ship the Go-level async unmap (§5.1). Pinning `CEPH_VERSION` back to `quincy` is **not** sufficient on its own — the udev wait code is identical, and the deeper culprit is elsewhere in the toolchain.

Ran a series of evidence-gathering probes on the live preprod plugin (no patching) to narrow what actually breaks event consumption.

```text
{}

{}

```

Each Create hits exactly the 2-minute internal `defaultShellTimeout` in `lib/sh.go`, even though the actual kernel device removal happened within ~230 ms (visible in host udev monitor).

### 6.6.5 Netlink socket state of the hung `rbd unmap`

```sh
cat /proc/$RBD_PID/fdinfo/3
# pos: 0  flags: 02004002  mnt_id: 9  ino: 292905408

grep -E 'Uid|Gid|NSpid|NSuid|NSgid|CapEff|State' /proc/$RBD_PID/status
# State:  S (sleeping)
# Uid:    0  0  0  0
# Gid:    0  0  0  0
# NSpid:  1972254  867
# CapEff: 00000000a82535fb

awk '$10==292905408 {print}' /proc/net/netlink
# (proto 15)   pid=867   groups=00000002   drops=0   inode=292905408
```

- Protocol 15 = `NETLINK_KOBJECT_UEVENT`.
- `groups=0x2` = subscribed to the **udev** broadcast group (correct — same as `udevadm monitor --udev`).
- `drops=0` = kernel did not drop any messages for this socket.
- `Uid=0, NSuid=0` in init userns. SCM_CREDENTIALS check should pass.

So the kernel believes the socket is correctly subscribed; the process is just not waking up to consume any data.

Kernel stack of the hung process:

```text
[<0>] do_poll.constprop.0+0x22a/0x390
[<0>] do_sys_poll+0x1c8/0x250
[<0>] __x64_sys_poll+0x3d/0x140
```

Open fds:

```text
3 -> socket:[292905408]                                  ← netlink udev monitor
6 -> /sys/bus/rbd/remove_single_major                    ← sysfs trigger (already written)
```

Strace attached and saw zero syscall activity over a 10 s window during which the kernel ran the full add+remove cycle. The `poll()` does not return — meaning either no `POLLIN` was raised for fd 3 in this process, or libudev's filter rejects everything received without taking it off the socket (less likely; would still cause `recvmsg` activity).

### 6.6.6 Adding `/run/udev` and populating its contents does NOT fix it

Tested progressively:

| Plugin variant                 | `/run/udev` mounted | `/run/udev/data` populated      | Create time |
|--------------------------------|---------------------|---------------------------------|-------------|
| stock image                    | no                  | no                              | 120 s       |
| `udevfix` (mount only)         | yes                 | no                              | 120 s       |
| `udevfix` + `apt install udev` | yes (host bind)     | yes (248 entries from host)     | 120 s       |

The `/run/udev` access path is not the missing piece for the rbd binary.

### 6.6.7 Where this leaves us

The bug is between:
- the netlink socket (events arrive, kernel sees them, `drops=0`)
- and libudev's userspace `udev_monitor_receive_device` inside the `rbd` binary (the process never returns from `poll`).

That gap is libudev’s own filtering / SCM_CREDENTIALS / `recvmsg` path. Two remaining suspects:

1. **`libudev1` 247 (bullseye) → 252 (bookworm)** — `udev_monitor_receive_device` had behavior changes around SCM credential checks and BPF filter compilation between those releases. Most plausible carrier.
2. **`rbd` binary linked against the newer libudev headers** at build time, picking up incompatible default filter setup.

Both shipped together in commit `a37705f` (the bullseye→bookworm + quincy→reef bump). The Ceph CLI source (`krbd.cc`) is byte-identical across pacific/quincy/reef, so this is *not* a Ceph-side change in udev handling — it’s the toolchain underneath.

## 6.7 Post-A/B: where the regression carrier actually lives

With the bullseye-quincy plugin reproducing the same 120 s hang, the breaking change is **not in the plugin image** at all. The plugin's `krbd.cc` udev-wait path has been the same since at least pacific, and the libudev underneath has always been one Debian generation old or so.

What changed must therefore be on the host side. Open hypotheses, in order of plausibility for an OVH OpenStack Ubuntu manager VM:

1. **Host kernel upgrade.** Block uevent delivery to non-init netns owners has had multiple kernel patches over 4.18 / 5.x / 6.x. Even though the plugin lives in init netns + init userns (verified in §6.6.1), the kernel's broadcast path for `NETLINK_KOBJECT_UEVENT` has changed how messages are filtered between the kernel thread and userspace listeners across recent stable releases. A kernel that broadcasts the "udev" channel only to listeners present at the moment the udev daemon re-broadcasts (i.e., a race with monitor setup) would produce exactly the observed pattern: `udevadm monitor` started before the event sees it, the rbd binary started after the kernel write doesn't.
2. **Host `systemd-udevd` upgrade.** A `udevadm` started before the event sees it; the rbd CLI starts its monitor after the kernel device is already partly through teardown. In newer systemd-udevd, the re-broadcast may now arrive on the netlink socket only for listeners that subscribed *before* the device existed. The rbd monitor subscribes only inside `do_unmap`, after the device add was processed.
3. **Lost orchestration that previously avoided the Create path.** If the Go API or backend used to pre-create rbd images via direct `rbd create` and only call `docker volume create` for the bookkeeping side, the slow path in the plugin was never on the hot path. Look at recent changes in `mydockergoapp/docker-api/` for volume handling.

### 6.7.1 The regression carrier is the host kernel upgrade

This host ran kernel **5.15.0-60-generic for 1015 days** (Feb 20 2023 → Dec 1 2025). That is the era when the plugin "worked perfectly". On Dec 1 2025 the host rebooted onto **5.15.0-161**, and on Jan 28 2026 onto **5.15.0-164** — the kernel still running now. The Jan 28 boot also re-started `systemd-udevd` (ActiveEnterTimestamp matches) and is the exact PID-1017-plugin start time observed in `ps -ef`.

Plugin behavior tracks 1:1 with this:

| Period                   | Kernel     | Plugin status (in retrospect)                       |
|--------------------------|------------|-----------------------------------------------------|
| Feb 2023 → Dec 1 2025    | 5.15.0-60  | "worked perfectly" (1015 days)                      |
| Dec 1 2025 → Jan 28 2026 | 5.15.0-161 | not tested; if Create was called, would have hung   |
| Jan 28 2026 → present    | 5.15.0-164 | confirmed hangs 120 s every Create                  |

Userspace point-upgrades during the same window (`systemd 249.11-0ubuntu3.12 → 3.16`, `ceph-common 17.2.7-...1 → ...2`) are sub-minor stable updates — extremely unlikely to change netlink uevent semantics. Kernel jump **5.15.0-60 → 5.15.0-161+** is the carrier.

Ubuntu's 5.15 kernel between those patch levels accumulated **~100 patch-level versions**, including HWE-derived backports. Areas plausibly relevant:

- `kobject_uevent` broadcast scoping
- `NETLINK_KOBJECT_UEVENT` `SCM_CREDENTIALS` attachment
- `rbd` / `libceph` kernel modules (krbd device removal sequencing)

The exact patch responsible is identifiable by bisecting Ubuntu's 5.15 changelog between -60 and -161 across those subsystems, but doing so does not change the remediation choice: the driver should not block on `rbd unmap`, full stop. The kernel-side change can be lived with via the Go-level async unmap (§5.1).

### 6.7.1.6 Open: which patch in 3.16 → 3.19 fixes it

Changelog inspection (Launchpad):

- `249.11-0ubuntu3.18`: Launchpad returns 404; never released.
- `249.11-0ubuntu3.19` (Mar 2026): CVE-2026-29111 fixes (path-util/cgroup, unrelated) **plus** a five-patch udev hardening set (no CVE assigned to the udev part).   - `1eba76668c` udev-builtin-net-id: print cescaped bad attributes
  - `cbd4b55380` udev: ensure tag parsing stays within bounds
  - `5973d3b1cc` udev: ensure there is space for trailing NUL before calling sprintf
  - `f038eb6c8b` udev: check for invalid chars in various fields received from the kernel
- `249.11-0ubuntu3.20` (later in 2026): adds `net_id` PCI-domain enhancement and `ID_NET_MANAGED_BY` udev property only. **No additional udev parser changes** relevant to this bug. Currently in `jammy-updates`.

### 6.7.1.6.5 Event-content probe — REFUTED two more hypotheses

Captured full property dumps on both hosts with `udevadm monitor --kernel --udev --property` while triggering a fresh rbd map+unmap.

**Finding 1**: preprod's remove event for the freshly-created `evdiag-probe2` image contains a malformed second devlink:

```text
DEVLINKS=/dev/rbd/mydocker-preprod/evdiag-probe2 /dev/rbd/mydocker-preprod/evdiag-probe2@
```

Cause: `/usr/bin/ceph-rbdnamer` (Ceph package shell script) reads `/sys/devices/rbd/<N>/{pool,name,current_snap}` and emits `pool/name@snap` if `snap != "-"`. On the udev REMOVE event, the udev daemon re-invokes the script — by that time the kernel has started teardown and `current_snap` reads empty (`""`). The script's check `if [ "$SNAP" != "-" ]; then echo -n "@$SNAP"; fi` triggers on empty too, appending a bare `@`. `SYMLINK+="rbd/%c"` in `50-rbd.rules` produces the malformed devlink.

`ceph-rbdnamer` and `50-rbd.rules` are **byte-identical between prod and preprod** (md5 confirmed: `e574be0fe1c8f2c9c577a2b634e79e51` and `de26654dd2c736fb8290d0e42b666304`). Same package, same bug exists on both. On prod the race against sysfs teardown happens to resolve before the trailing `@` is generated.

**Test C**: disabled `50-rbd.rules` entirely on preprod (`mv ...rules ...rules.disabled; udevadm control --reload-rules`). New test: `norule-probe` (rbd39). Captured events have **no `DEVLINKS` field at all** — completely clean events. The host's `time rbd unmap "$DEV"` still hung 120 s.

So the udev rule + script interaction is **NOT** the carrier. The malformed devlink is a separate latent bug in `ceph-rbdnamer` (worth filing upstream against Ceph) but is not what hangs the rbd CLI.

Four hypotheses tried, all refuted by evidence on the same host:

| Hypothesis                                            | Refuted by                                                                                                                                                  |
|-------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Ceph CLI version (pacific/quincy/reef) change         | `krbd.cc` is byte-identical across versions                                                                                                                 |
| Host kernel `5.15.0-60` → `5.15.0-161/164`            | prod runs `5.15.0-164` and works in <1 s                                                                                                                    |
| Host systemd/udev 3.16 → 3.19 patch series            | the 3.19 patches touch builtins (scsi_id, net_id, ...) and devlink creation, not netlink monitor; prod-vs-preprod userspace correlation may be coincidental |
| Malformed udev devlinks from `ceph-rbdnamer` race     | rule disabled → still hangs 120 s on completely clean events                                                                                                |

Where the bug actually lives: somewhere between netlink event delivery (verified working) and libudev's `udev_monitor_receive_device` returning a match for the rbd CLI's `UdevUnmapHandler`. Whatever it is, it is environmentally triggered on `tf-preprod-manager` and not on `prod-manger` despite all visible state matching (same image binaries, same kernel module srcversion, same scripts, same rules, same `/etc/ceph/`, same Ceph cluster, shared netns).

Further investigation paths still require either:

- Invasive host-side experimentation (apt upgrade systemd/udev/libudev1 after VM snapshot rollback prepared — `systemd 249.11-0ubuntu3.16 → 249.11-0ubuntu3.20`, would need a maintenance window),
- Reproducing on a fresh throwaway Ubuntu 22.04 jammy VM in OVH targeting the same Ceph cluster + same plugin to confirm whether the bug travels with the host distribution or is unique to this VM's accumulated state,
- Or strace-style libudev internal capture (already attempted; rbd CLI poll deadlock makes attach unreliable).

Cost-benefit of further investigation is now poor relative to shipping the §5.1 sysfs-poll fix. The fix is correctness-preserving, decouples the driver from this host-side bug entirely, and works regardless of which subsystem ultimately turns out to be at fault.

### 6.7.1.7 Operational decision: do not apt-upgrade preprod systemd as the experiment

systemd/udev on a Docker Swarm manager is load-bearing. An apt upgrade that wedges PID 1 services has the blast radius of the whole manager. Investigation paused at this point. The remediation choice does not depend on closure of "why now" — the Go-level async unmap (§5.1) removes our dependence on host-side udev event delivery entirely, which is the right fix regardless of which systemd commit lands the fix or whether it's even fixed upstream.

If we want to confirm the systemd hypothesis later without risking preprod:

- **VM snapshot first**, then apt upgrade systemd/udev/libudev1, then test.
- **Or** spin up a throwaway Ubuntu 22.04 VM at `249.11-0ubuntu3.16` (or whatever ships in stock jammy today), install the plugin, reproduce. Then upgrade in place on that throwaway and re-test.
- **Or** inspect `apt-get source systemd` patches inline (no install) to confirm the udev patch touches the relevant netlink monitor path.

### 6.7.2 Why nobody noticed during Dec 1 → Jan 28

The bullseye+quincy build is byte-for-byte the same as it was years ago and still hangs (§6.6.8). So the plugin's `Create` would have been broken from Dec 1. Nobody noticed because:

- `docker volume create` is not on the hot path for student lab provisioning (the backend orchestrates differently; see grep below).
- The Jan 28 zombie was probably one of many — earlier ones may have been cleaned up by host reboot or someone re-installing the plugin without diving into root cause.

The orchestration check on the Go backend confirms (or refutes) this:

```sh
# run on the dev workstation where mydockergoapp is checked out,
# OR on a host that has the Go API source
grep -RIn 'VolumeCreate\|VolumeMount\|VolumeRemove\|docker volume' \
  /path/to/mydockergoapp/docker-api/
```

If results show direct `rbd` CLI calls or pre-created images rather than `client.VolumeCreate(...)`, that confirms the plugin's Create endpoint was rarely exercised in production.

### Why the plugin appeared to "work" before

The bullseye+quincy build hangs exactly the same as the bookworm+reef one. That means in production it has *always* hit the 2-minute timeout on `Create` and `Unmount`. Two explanations are compatible with users not noticing for years:

- **Backend pre-creates RBD images** via direct `rbd` CLI on a Docker Swarm manager, not via the volume plugin's `Create` endpoint. In that case the plugin is only called for `Mount`/`Unmount` lifecycle. `Mount` does map+mkfs and returns — no unmap. `Unmount` runs at container teardown when nobody is waiting on the result; dockerd's 2-minute timeout fires but the container destruction continues in the background and no error is surfaced to the user.
- **Sample bias.** Manual `docker volume create` was never run regularly. The current report is the first time anyone tried it under realistic conditions.

Verifying the orchestration path is a single grep in the Go backend (`mydockergoapp/docker-api/`) for `docker volume create` / `VolumeDriver` references.

## 7. Operational notes uncovered during the investigation

These are not the cause of the timeout but were spotted while debugging and are worth fixing/monitoring.

- **Stale zombie plugin processes.** The old plugin (`PID 1017`, started Jan 28) accumulated many defunct `[rbd]` children (`[rbd] <defunct>` from Mar/May). Indicates the driver has been crashing repeatedly over months and nobody noticed. Source likely the same unmap hang — every Create accumulated one leaked rbd zombie, eventually triggering pid table pressure / OOM until plugin itself died. Monitor `ps -ef | grep '\[rbd\] <defunct>'` post-fix.

- **Stale containerd / runc / cgroup state.** Forcing recovery of the zombie plugin required cleaning:
  - `/run/containerd/io.containerd.runtime.v2.task/plugins.moby/<id>/` (stale shim bundle)
  - `runc-<id>.scope` systemd unit (cgroup pinned by un-reaped zombies)
  - `ctr -n plugins.moby tasks/containers` namespace entries

  In the long run, fixing §5.1 should prevent the recurrence loop.

- **Docker plugin manifest format ≠ source format.** The `config.json` at `/var/lib/docker/plugins/<id>/config.json` is the runtime manifest (`.plugin.Config`, with TitleCase keys and `rootfs` as a layer object). It is **not** consumable by `docker plugin create` directly; the source `config.json` in this repo is the right input.

- **Plugin shell environment is BusyBox-sh.** No `time` builtin. Use `date +%H:%M:%S.%N` markers for in-plugin timing.
